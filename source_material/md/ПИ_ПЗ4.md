   # **Краткая теория**
   ## **Зачем проекту контроль версий**

   При обмене файлами через сообщения легко перепутать актуальные версии, потерять исправление или одновременно изменить разные копии одного документа. Система контроля версий помогает сохранять состояния проекта, сравнивать их и выяснять, когда и кем внесены изменения. Это полезно для программного кода, требований, сценариев и текстовых исходников диаграмм. [1]

   Репозиторий Git содержит историю зафиксированных состояний отслеживаемых файлов. Рабочая папка – место, где участник редактирует файлы; служебные данные локального репозитория обычно находятся в каталоге .git. Редактирование файла ещё не означает, что изменение включено в историю.

   Обычное файловое хранилище тоже может поддерживать историю версий. Поэтому отличие заключается не в одном наличии старых копий, а в организации согласованных изменений проекта, веток и их объединения.

   ## **Git и площадка размещения**

   Git – распределённая система контроля версий. При обычном полном клонировании участник получает локальный репозиторий с историей, поэтому может создавать коммиты и просматривать историю без постоянного соединения с сервером. Интернет нужен для обмена изменениями с удалённой площадкой. [2]

   GitHub, GitLab, Bitbucket и другие сервисы размещают удалённые Git-репозитории. Площадка может предоставлять учётные записи, права доступа, задачи, обсуждения, запросы на слияние и автоматические проверки. Эти возможности дополняют Git; их доступность зависит от выбранного сервиса. Для данной работы выберите площадку с ветками, запросами на слияние и доступом преподавателя.


   ## **Основные способы работы с Git**

   Командная строка позволяет явно выполнять операции Git и видеть их результаты. Графический клиент показывает состояние файлов, историю и ветки через интерфейс. Среда разработки часто предоставляет те же действия рядом с редактором кода. Веб-интерфейс площадки удобен для просмотра файлов, постановки задач и обсуждения изменений. Названия кнопок различаются, но смысл операций остаётся тем же.

   В этой работе допустим терминал или графический клиент. При защите нужно объяснить выполненные операции. Одна загрузка файлов через браузер не демонстрирует получение локального репозитория и обмен изменениями между участниками.


   ## **Рабочая папка индекс и коммит**

   Рабочая папка содержит редактируемые файлы. Индекс, или staging area, задаёт содержимое следующего коммита: участник выбирает, какие изменения включить. Коммит фиксирует подготовленное состояние и сопровождается авторством, сообщением и идентификатором. Один коммит должен выражать понятный шаг, например уточнение предусловий UC-02. [2, 3]

   Операция add подготавливает выбранное содержимое файла. Если после неё продолжить редактирование, новые правки не попадут в коммит до повторного add. Команда status помогает увидеть это различие. Сообщение «обновление» малоинформативно; сообщение «Уточнены причины отказа в UC-02» объясняет результат.


   ## **Локальный и удалённый репозитории**

   Локальные коммиты остаются на компьютере участника до отправки. Push передаёт коммиты и обновляет ветку удалённого репозитория. Fetch получает сведения и данные об удалённых изменениях, но сам по себе не объединяет их с текущей рабочей веткой. Pull получает изменения и интегрирует их; способ интеграции зависит от параметров и настроек. В примерах ниже используется pull --ff-only, который отказывается от обновления при расхождении истории. [4, 5]

   Имя origin обычно обозначает удалённый репозиторий, из которого сделан клон. Это условное имя, а не название площадки. Получение ZIP-архива с файлами не равно клонированию: архив обычно не содержит историю Git и настройки связи с удалённым репозиторием.
   ## **Ветки слияние и взаимная проверка**


   Ветка задаёт отдельную линию работы. В учебном проекте основная ветка main содержит согласованные результаты, а изменения выполняются в тематических ветках. Если команда использует другое имя основной ветки, заменяйте main в примерах этим именем. Ветки не требуют ручного создания копий всей папки проекта. [6]

   Запрос на слияние – предложение включить изменения одной ветки в другую. На разных площадках он называется Pull Request или Merge Request. Участники просматривают разницу, обсуждают содержание и вносят исправления. Создать запрос и выполнить слияние – разные действия. [8]

   Конфликт возникает, когда Git не может автоматически объединить изменения, например при разных правках одной строки. Участники выбирают согласованное содержание и завершают слияние. Автоматически успешное слияние ещё не гарантирует смысловую согласованность: требование и сценарий могут противоречить друг другу в разных файлах.


   ## **README Markdown и исключаемые файлы**

   README.md объясняет назначение раздела и помогает найти материалы. Markdown – текстовый формат с простыми обозначениями заголовков, списков и ссылок. Корневой README представляет весь проект; README разделов содержит подробности. В этой работе docs/README.md дополнительно содержит полный общий отчёт. Изменения текстовых файлов удобно сравнивать по строкам. История DOCX тоже сохраняется: можно найти коммит и восстановить прежнюю версию файла. Ограничение состоит в том, что обычные средства Git не показывают содержимое DOCX как удобную построчную разницу и не объединяют его так же, как Markdown.

   Markdown становится основным редактируемым вариантом отчёта по соглашению команды. Git отслеживает и другие файлы: код, тесты, исходники диаграмм, изображения и Word-документы. Выбирайте состав коммита по смыслу задачи; правило «коммитить только MD» не применяется.

   Файл .gitignore задаёт правила исключения неотслеживаемых файлов: временных документов, локальных настроек и результатов сборки. Он не удаляет из истории уже добавленные данные и не прекращает автоматически отслеживать существующий файл. Пароли, токены и закрытые ключи в репозиторий не помещают. Для настроек можно хранить пример без секретных значений. [7]


   ## **Задачи тесты и автоматические проверки**

   Задача на площадке описывает работу: что требуется изменить, кто отвечает и по каким признакам результат будет принят. Ссылки между задачей, коммитом и запросом на слияние помогают проследить решение. В этой работе фиксируйте задачу в описании запроса; если площадка поддерживает трекер задач, используйте его.

   Тестовый случай описывает предусловия, действия и ожидаемый результат. Автоматический тест выполняет проверку программно. Линтер проверяет код по заданным правилам. CI организует автоматические проверки изменений; CD относится к доставке или развёртыванию. В этой работе достаточно понимать назначение этих средств. Наличие папки tests не означает, что автоматическое тестирование уже настроено; настройка CI/CD является дополнительным заданием.

   ## **Назначение разделов**

   source-material – предоставленные задания, исходные данные и разрешённые к размещению вспомогательные материалы. В README укажите происхождение и назначение файлов. Эта папка не заменяет каталог исходного кода.

   docs – документация и отчётность команды. Непосредственно в docs размещайте report.docx – общий отчёт Word для сдачи, а в docs/README.md – полный общий отчёт Markdown с оглавлением и навигацией. Папка docs/doc содержит индивидуальные отчёты Word; docs/md – их рабочие Markdown-версии и дополнительные текстовые материалы. В docs/img находятся изображения для отчётов, в docs/draw – редактируемые исходники диаграмм, включая .drawio и .puml. Сохраняйте идентификаторы требований и сценариев из предыдущих ПЗ.

   projects – программная часть продукта. Каталог projects/src содержит код приложения, projects/docs – описание реализации, настройки и запуска. README раздела объясняет состав программы и порядок работы с ней. Если кода ещё нет, честно укажите текущий этап и запланированное наполнение.

   modules – отдельно разрабатываемые компоненты. README перечисляет имеющиеся или планируемые модули и объясняет их связь с projects/src. Не храните одинаковый код одновременно в обоих разделах.

   tests – тестовые случаи и, по мере появления реализации, автоматические тесты. README описывает их расположение, порядок выполнения и способ фиксации результатов. Невыполненные проверки отмечайте как запланированные.

   teams – сведения об участниках, их ролях и ответственности. В img размещайте необходимые изображения команды, если они используются. Фотографии участников не являются обязательными.

Используйте заголовки и ссылки на изображения, чтобы длинный текст было удобно читать.

   ## **Правила командной работы**

   В CONTRIBUTING.md зафиксируйте имя основной ветки, способ именования тематических веток, требования к сообщениям коммитов, состав описания запроса на слияние, порядок проверки и ответственного за подготовку Word-версий. Исходник диаграммы и соответствующее изображение обновляются вместе. Если содержательная правка впервые сделана в Word, перенесите её в Markdown и повторно подготовьте Word-версию. Только исправления оформления допустимо выполнять непосредственно в DOCX.

   Индивидуальный отчёт описывает задачу конкретного участника, связанные ФТ и UC, принятые решения, собственный результат, проверку и вклад в работу команды. Общий отчёт представляет согласованное состояние всего проекта. Укажите авторство, но устраните повторяющиеся введения, противоречия и разные названия одних сущностей; простого соединения индивидуальных текстов недостаточно.

   Соответствие версий: docs/README.md → docs/report.docx; docs/md/ivanov-report.md → docs/doc/ivanov-report.docx. Текст, таблицы, диаграммы и выводы в каждой паре должны совпадать по содержанию. Навигационные ссылки и оформление могут различаться в зависимости от формата.

1. 1. Каждый участник переносит свою часть предыдущих работ в Markdown-отчёт и отмечает связанные требования, сценарии и диаграммы. Сохраните содержательные результаты предыдущих ПЗ.
1. 1. В той же тематической ветке обновите затронутый раздел docs/README.md, исходники диаграмм и изображения. Общий отчёт должен отражать согласуемое изменение.
1. 1. Перед сдачей ответственный обновляет Word-версии из согласованного Markdown, проверяет содержание и оформление, затем фиксирует готовые документы. В сообщении коммита обозначьте экспорт; содержательные изменения не маскируйте под переоформление.

   Во время работы Word-версия может отставать. В начале docs/README.md указывайте её статус: «требует обновления» или «сверена с Markdown перед сдачей». Перед сдачей все пары должны быть сверены. Для индивидуальных отчётов отметьте результат сверки рядом со ссылками. Это позволяет отличить рабочий текст от подготовленной версии для проверки.


   ## **Подготовка Word из Markdown**

   Выберите доступный команде способ: конвертер с поддержкой DOCX, например Pandoc, либо перенос отрисованного Markdown в Word с применением согласованных стилей. Редактор Markdown сам по себе не обязательно умеет экспортировать DOCX. Не копируйте сырой текст с символами разметки вместо заголовков и списков.

   При использовании Pandoc сначала установите его по официальной инструкции. Следующий пример выполняется из папки docs: конвертер читает README.md, ищет изображения относительно этой папки и записывает report.docx. Закройте редактируемый report.docx перед экспортом. Команда не настраивает автоматически все требования к оформлению. [10]

   **Листинг 3 – Подготовка общего отчёта Word**

   **pandoc --version**

   **pandoc README.md -o report.docx**

   Для индивидуального отчёта задайте входной путь md/ivanov-report.md и выходной doc/ivanov-report.docx. Ссылки на изображения в исходном Markdown должны работать при чтении на площадке; если конвертер не находит изображения, настройте пути поиска ресурсов по его документации. Для повторяемого оформления Pandoc поддерживает параметр --reference-doc с заранее подготовленным DOCX-образцом. [10]

1. 1. Сверьте текст, таблицы и состав рисунков с Markdown. В Word должны быть сами изображения, а не только ссылки на файлы.
1. 1. Проверьте стили заголовков, поля, шрифты, интервалы, нумерацию страниц и списков. Оглавление должно соответствовать разделам.
1. 1. Просмотрите каждую страницу: подписи не оторваны от объектов, таблицы и код не обрезаны, рисунки читаются. Исправления содержания сначала внесите в Markdown; при повторном экспорте заново проверьте оформление.
1. 1. Зафиксируйте Word-версии и отметки сверки. В итоговом сообщении сдачи укажите коммит, содержащий согласованные Markdown, DOCX и связанные материалы.

   # **Базовые операции Git**

   В таблице приведены команды и их назначение. Выполняйте их из локальной папки репозитория, кроме первоначального клонирования. Команды справки позволяют уточнить параметры: git help или git help commit. [3–7]

   **Таблица 2 – Основные команды**

   |**Команда**|**Назначение**|
   | :-: | :-: |
   |git --version|Проверить наличие и версию Git|
   |git clone URL|Создать локальную копию удалённого репозитория|
   |git init|Создать репозиторий в локальной папке; после clone не требуется|
   |git status|Посмотреть ветку и состояние файлов|
   |git diff|Посмотреть изменения отслеживаемых файлов вне индекса|
   |git add PATH|Подготовить выбранное содержимое к коммиту|
   |git diff --staged|Проверить изменения, подготовленные к коммиту|
   |git commit -m "Текст"|Создать локальный коммит из подготовленного содержимого|
   |git log --oneline|Просмотреть краткую историю коммитов|
   |git switch -c NAME|Создать ветку и перейти в неё|
   |git switch main|Перейти в существующую основную ветку|
   |git remote -v|Посмотреть адреса удалённых репозиториев|
   |git fetch origin|Получить удалённые изменения без слияния в рабочую ветку|
   |git pull --ff-only|Получить изменения и обновить ветку без создания слияния; при расхождении остановиться|
   |git push -u origin NAME|Опубликовать ветку и установить связь с удалённой веткой|
   |git merge NAME|Объединить указанную ветку с текущей|


   **Пример рабочего цикла\
   (просто учебный пример, как мы работаем с репозиторием)**
   ---------------------------------------------------------

   Создайте на площадке репозиторий с начальным README и основной веткой main. Скопируйте его URL. В следующих командах замените URL адресом, project-name – именем папки клона, а имя и адрес автора – собственными данными. Значения в примерах не являются готовыми учётными данными. Настройки автора не выполняют вход на площадку; способ аутентификации выбирается по её документации. [9]

   **Листинг 4 – Получение репозитория и настройка автора**

   **git clone URL**

   **cd project-name**

   **git config user.name "Имя Фамилия"**

   **git config user.email "Адрес автора коммитов"**

   **git remote -v**

   **git status**

   Перед новой задачей проверьте, что незавершённые изменения сохранены осмысленным коммитом в своей ветке. Затем обновите основную ветку и создайте тематическую. Если pull --ff-only сообщает о расхождении, остановитесь и выясните причину; принудительная отправка не является способом исправить такую ситуацию.

   **Листинг 5 – Подготовка и публикация изменения**

   **git switch main**

   **git pull --ff-only**

   **git switch -c docs/uc-02**

   **# Измените файл docs/md/UC-02.md в редакторе**

   **git status**

   **git diff**

   **git add docs/md/UC-02.md**

   **git diff --staged**

   **git commit -m "Уточнены предусловия UC-02"**

   **git push -u origin docs/uc-02**

   Файл и ветка в примере условные: используйте свой сценарий и собственное содержательное изменение. Новый неотслеживаемый файл не появится в обычном git diff; после add его содержимое можно проверить через git diff --staged.

   В веб-интерфейсе создайте запрос из docs/uc-02 в main. Укажите цель, связанные требование и UC, изменённые файлы и способ проверки. Другой участник просматривает результат, оставляет содержательный отзыв и проверяет исправления. После согласования выполните слияние средствами площадки. Затем локально перейдите в main, выполните git pull --ff-only и убедитесь, что принятый файл появился. При таком порядке дополнительный локальный git merge не нужен.
