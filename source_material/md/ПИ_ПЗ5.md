**ПРОГРАММНАЯ ИНЖЕНЕРИЯ**

**Практическое задание № 5**

**«Разработка индивидуального программного модуля»**

Продолжите разработку программного продукта, выбранного командой в ПЗ № 1.

К началу работы команда уже должна иметь сформулированные функциональные и нефункциональные требования, описанные варианты использования, UML-диаграммы, общий Git-репозиторий, структуру проекта и распределение ответственности между участниками.

В данной практической работе начинается этап программной реализации. Каждый участник команды должен самостоятельно разработать один небольшой программный модуль, соответствующий части функциональности проектируемой системы.

Разработка каждого модуля выполняется в отдельной ветке Git. В этой работе индивидуальные ветки не объединяются.

**Задание 1. Выбор реализуемого функционального фрагмента**

Каждый участник выбирает функциональность, связанную с ранее разработанными материалами.

Модуль должен быть связан как минимум с функциональным требованием, вариантом использования и ранее подготовленной диаграммой последовательностей.

Функциональное требование

↓

Вариант использования

↓

Диаграмма последовательностей

↓

Программный модуль

Пример связи:

ФТ-03

Регистрация заявки

↓

UC-03

Создание заявки

↓

SD-03

Последовательность создания заявки

↓

Модуль

request_creation

Нельзя выбирать совершенно новую функцию, которой не было в требованиях проекта. Если в процессе реализации выясняется, что требования необходимо изменить, изменение должно быть зафиксировано и согласовано.

**Задание 2. Распределение модулей внутри команды**

Каждый участник команды должен реализовывать собственный функциональный модуль. Модули не должны полностью дублировать друг друга, но должны относиться к одному программному продукту.

Пример распределения для условной информационной системы:

| Участник   | Модуль                   |
| ---------- | ------------------------ |
| Участник 1 | Регистрация пользователя |
| Участник 2 | Создание заявки          |
| Участник 3 | Поиск объектов           |
| Участник 4 | Изменение статуса заявки |

Конкретные модули определяются функциональностью вашего проекта. В следующей работе они должны быть пригодны для объединения в одну систему.

**Задание 3. Согласование технической основы проекта**

До начала программирования команда должна согласовать общие технические решения.

- язык программирования;
- используемую версию языка;
- при необходимости – используемый фреймворк;
- способ запуска программы;
- основные правила именования файлов, классов и функций;
- формат данных, которыми в дальнейшем смогут обмениваться модули.

Пример:

Язык: Python 3.12

Формат данных: объекты/словари Python

Идентификаторы: целые числа

Имена функций: snake_case

Кодировка: UTF-8

Все участники должны использовать совместимый стек. Не допускается разрабатывать части одной программы на несовместимых технологиях без заранее спроектированного способа взаимодействия. В данном проекте нет строгой привязи к языку Python, выбрать можно любой стек технологий.

**Задание 4. Определение интерфейса модуля**

До написания программного кода кратко опишите назначение своего модуля.

1. название модуля;
2. связанное функциональное требование;
3. связанный вариант использования;
4. назначение;
5. какие данные модуль принимает;
6. какой результат должен формировать;
7. какие ошибки или некорректные данные могут возникнуть.

Пример:

Модуль: Создание заявки

Связанные требования:

ФТ-03

Вариант использования:

UC-03 Создание заявки

Входные данные:

– название заявки;

– описание;

– категория;

– пользователь.

Результат:

созданная заявка с идентификатором.

Ошибочные ситуации:

– отсутствует название;

– неизвестная категория;

– некорректные данные пользователя.

Описание должно соответствовать ранее разработанным требованиям и UML.

**Задание 5. Создание индивидуальной ветки**

Перед началом реализации получите актуальное состояние основной ветки:

git switch main

git pull --ff-only

После этого каждый участник создаёт собственную тематическую ветку. Рекомендуемый формат:

feature/&lt;название-модуля&gt;

Например:

git switch -c feature/create-request

git switch -c feature/user-registration

Проверьте текущую ветку:

git branch

Разработка собственного модуля должна выполняться только в своей тематической ветке.

**Задание 6. Разработка программного модуля**

Реализуйте выбранный функциональный фрагмент.

Модуль должен содержать реально работающую программную логику, а не только пустые классы или функции. Не устанавливается обязательное количество строк кода: объём определяется задачей проекта.

Модуль должен:

- принимать данные;
- выполнять предусмотренную требованиями обработку;
- формировать наблюдаемый результат;
- обрабатывать как минимум основные некорректные входные данные;
- запускаться независимо для проверки своей основной функции.

Не требуется реализовывать весь программный продукт.

Пример логики модуля создания заявки:

получить данные

↓

проверить обязательные значения

↓

сформировать заявку

↓

присвоить идентификатор

↓

вернуть результат

Если модуль отвечает за поиск, структура может быть иной:

получить критерии поиска

↓

проверить параметры

↓

выполнить поиск

↓

сформировать результат

Конкретный алгоритм определяется проектом команды.

Задание 7. Реализация ввода данных

Каждый модуль должен предоставлять возможность ввести исходные данные для проверки его работы.

Допускается:

- консольный ввод;
- форма веб-интерфейса;
- графическая форма;
- параметры функции;
- загрузка документа для обработки;
- другой согласованный интерфейс.

Например, консольный модуль может запрашивать:

Введите название:

Введите категорию:

Введите описание:

Веб-приложение может использовать соответствующую форму.

Возможность ввода данных создаётся не только для демонстрации программы. Она потребуется для разработки тестовых случаев и проверки поведения программного обеспечения, а также автоматизации тестирования.

Должна существовать возможность проверить как минимум:

корректные данные

некорректные данные

граничные значения

Полноценное тестирование в данной работе пока не выполняется.

Задание 8. Не объединять модули преждевременно

Необходимо получить структуру вида:

main

│

├── feature/module-a

│ └── модуль участника 1

│

├── feature/module-b

│ └── модуль участника 2

│

├── feature/module-c

│ └── модуль участника 3

│

└── feature/module-d

└── модуль участника 4

На данном этапе не требуется, чтобы один модуль вызывал другой. Не создавайте общий объединяющий код заранее.

Задание 9. Размещение программного кода в репозитории

Используйте структуру репозитория, подготовленную в ПЗ № 4.

Для индивидуально разрабатываемых компонентов используется раздел:

modules/

Для каждого модуля создайте отдельный каталог, например:

modules/

├── user-registration/

├── create-request/

├── search/

└── status-management/

В каталоге конкретного модуля должны находиться исходный код, README.md и при необходимости вспомогательные файлы.

Не помещайте временные файлы среды разработки, кэш, виртуальное окружение и локальные настройки.

Задание 10. README индивидуального модуля

Каждый участник создаёт краткий README.md своего модуля.

\# Название модуля

\## Разработчик

ФИО

Что делает модуль.

\## Связанные требования

ФТ-XX

\## Связанный вариант использования

UC-XX

\## Входные данные

Какие данные принимает модуль.

\## Результат

Что является результатом работы.

\## Запуск

Как запустить модуль.

Что реализовано и какие ограничения пока существуют.

README должен описывать фактическую реализацию, а не план на будущее.

После реализации сопоставьте фактическое поведение программы с материалами предыдущих работ.

UC

Если реализация потребовала уточнения требований, это изменение необходимо зафиксировать в документации проекта.

Задание 12. Фиксация реализации в Git

После реализации проверьте состояние репозитория:

git status

Посмотрите изменения:

git diff

Добавьте только относящиеся к своей задаче файлы. Например:

git add modules/create-request

Проверьте подготовленный коммит:

git diff --staged

Создайте содержательный коммит:

git commit -m "Реализован модуль создания заявки"

При необходимости работа может содержать несколько логически разделённых коммитов.

Сообщения «update», «fix», «работа», «готово» считать недостаточно информативными.

Задание 14. Публикация индивидуальной ветки

Опубликуйте ветку:

git push -u origin feature/create-request

Проверьте через веб-интерфейс площадки:

- ветка существует;
- коммиты отображаются;
- автор коммитов определён правильно;
- исходный код доступен;
- README отображается;
- изменения относительно main видны.

Важно: не выполняйте merge своей ветки в main.

К концу ПЗ № 5 в репозитории должны одновременно существовать отдельные ветки участников.
